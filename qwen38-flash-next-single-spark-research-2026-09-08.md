# Qwen3.8-Flash-Next on one Spark: recipes for the factory Player

**Researched 2026-09-08.** Public recipes, source files, image manifests and model metadata inspected; no model downloaded or served on the estate. The resulting procedure is [RUNBOOK-qwen38-flash-next-seat.md](./RUNBOOK-qwen38-flash-next-seat.md).

Start with **travelinlance Hybrid Sharp v2 on patched vLLM**, on dedicated `spark-fcf6`, keeping the factory and its tuned seats on the Dell. This is a recommendation for the first controlled trial, **not a finding that it is the fastest or most accurate model**. Its published recipe supplies an immutable image, intact disk-backed PLE lookup table, and fixes for prefix reuse and tool choice. The factory needs those properties before a decode-speed advantage is useful.

Speculative acceptance changes with the prompt and sampling; some recipes change PLE, side layers, KV precision or templates; some report sums across requests. That is useful performance evidence, not an engine-only experiment. ## The shared Spark Arena result, resolved

The page's embedded benchmark data was accessible over HTTPS even though the browsing renderer failed and the separate raw-download endpoint returned 403. The entry was submitted **2026-08-31 10:36:33 UTC**. Its **23.3276 tok/s** row is `tg128 @ d65535 (c1)`, consistent with the shared **23.33**. The current page summary rounds a different short-context value to **23.4**. The 65,535-depth cold-context prefill row is 1,859.23 tok/s / 35.25 seconds; its subsequent `pp2048` row is a different measurement. Five-stream `tg128 (c5)` is **75.02 aggregate**, not that speed per user. At 100K depth / ten streams, `tg128` falls to **1.79 aggregate**. Thus `max_num_seqs=8` is not proof that eight long factory conversations fit efficiently. [Full benchmark](https://spark-arena.com/benchmark/7ec7eaf7-a10c-403d-be52-c44c0fc64539).

The pinned [v2 recipe](https://github.com/lancelind/qwen3.8-Flash-DGX/blob/4e1b246aa141e04bd45c20bd1334512988c3770b/recipes/qwen38-flash-hybrid-sharp-v2-vllm.yaml) matches that entry: context 262,144, eight sequences, 8,192-token prefill chunks, utilisation 0.75, BF16 KV (`auto`), prefix cache, exact top-k, GPU PLE gathering, and **no speculation**. The lower reservation leaves memory for the operating system's page cache. Do not transplant Tony's FP8-KV or MTP flags into it: the engine versions, patches and parsers differ.

The model's PLE table remains intact in this recipe. Its FP8 side-layer conversion and Sharp template **do** change the candidate relative to the original model. The small published template test reported 18% fewer output tokens on four prompts; that does not establish general quality preservation. Name the exact checkpoint and template in results, not just “Qwen 3.8.” [Model card](https://huggingface.co/travelinlance/Qwen3.8-Flash-Next-RadixArk-NVFP4-Hybrid-Sharp/blob/1f2ba8b30e34097058610938864b1991cfffa24b/README.md).

## Why Tony is the second serving trial

The [actual TP1 launcher](https://github.com/tonyd2wild/Qwen3.8-Flash-Next-NVFP4-DGX-Spark/blob/6ad1c8f15cbab1ababd2048e8e5f94094dbfc4a0/single-spark-vllm-tp1/launch/qwen38fn-nvidia-tp1.sh) pins nightly `8a728663c1c3eeace834a95f5654fa653cc1998c`, serves `nvidia/Qwen3.8-Flash-Next-NVFP4`, and uses `qwen3_xml` tool parsing. It defaults to staged PLE, compile-off decode graphs, MTP3, 65,536 draft-vocabulary IDs, six sequences, 4,096-token chunks, utilisation 0.80, FP8 KV, and thinking off. Its `PREFIX_CACHE_ARG` default is `--no-enable-prefix-caching`, citing [vLLM #54173](https://github.com/vllm-project/vllm/issues/54173).

That makes it worth benchmarking, but poor grounds for promising a faster factory today. The source also hardcodes model and patch directories and drops host caches at launch. A future Tony runbook must stage **all** overlays at the pinned commit, freeze its image digest, and prove long-prefix correctness before enabling caching. Running that launcher with different weights or simply flipping its cache flag would be a new, unvalidated recipe. The NVIDIA checkpoint revision observed was `fc694b54fb0174e0913e6adf86691ef85a4ead47`; it is distinct from the RadixArk-derived model. [Checkpoint metadata](https://huggingface.co/api/models/nvidia/Qwen3.8-Flash-Next-NVFP4).

## Forum findings that become gates

- **Long-context silent corruption:** the retained TP2 record reports token-zero loops past roughly 120K despite successful HTTP responses. Its staged fix was not validated on that lane. This warrants actual long-context content checks; a healthy endpoint is insufficient. [Tony's incident/limitations record](https://github.com/tonyd2wild/Qwen3.8-Flash-Next-NVFP4-DGX-Spark/blob/6ad1c8f15cbab1ababd2048e8e5f94094dbfc4a0/lanes/sglang-tp2/KNOWN-ISSUES-thinking-tool-loop.md).
- **Cache hits can return wrong answers:** blazux documents the Mamba block-size error, a separate state-copy race, and sparse-attention nondeterminism. Test repeated prefixes, a changed suffix, unrelated requests and real tool continuations. The image containing a patch is not proof that every workload is fixed. [Implementation notes](https://github.com/blazux/qwen3.8-Flash-DGX/blob/2d9b5b744b8b8e25e0c40120f4a13bcec3554aa9/docs/HOW-IT-WORKS.md).
- **Benchmark context matters:** the “44 tok/s” SingleSpark thread originally measured at 8K, subsequently moving its default to 64K. Neither establishes 128K factory performance. [Author's context clarification](https://forums.developer.nvidia.com/t/fitting-qwen3-8-flash-next-180b-onto-one-dgx-spark-44-tok-s-at-four-bits/382117/3), [64K update](https://forums.developer.nvidia.com/t/fitting-qwen3-8-flash-next-180b-onto-one-dgx-spark-44-tok-s-at-four-bits/382117/7).
- **Do not edit downloaded HF blobs:** a forum experiment changes `indexer_budget` and `indexer_compress_ratio` in place. Those are model-behaviour changes, not established corrections for this trial. The runbook hashes the control files and retains 2048 / 4. [Experiment and reported measurements](https://forums.developer.nvidia.com/t/qwen3-8-flash-next/381228/260).
- **“Best thread” is a discovery aid:** it usefully collects alternatives but includes subjective recommendations and disputes about quantization. Follow its links to the authors' configurations and receipts. [Comparison thread](https://forums.developer.nvidia.com/t/which-single-spark-qwen3-8-flash-next-thread-is-the-best/382522).

## The factory experiment this supports

The [September 4 bigger-coder research](../ai-transition/docs/bigger-coder-models-research-2026-09-04.md) names this exact two-box shape. The Dell keeps the tuned Gemma seats; the Spark's tutor fleet is displaced temporarily. The baseline is **Qwen3.6-35B-A3B, UD-Q4_K_XL, llama.cpp, `qwen36-workhorse`**, thinking off, 131,072-token context. The recorded coder runs around 51 tok/s in builds; over half the calls in the workload assessment exceed 64K prompt tokens. The [build-cost measurement](../ai-transition/docs/measurements/what-a-build-costs-the-models-2026-09-01.md) establishes that LiteLLM records, rather than GB10's unreliable utilisation display, are the useful timing source.

There are two relevant experiment records, which must not be conflated:

1. The earlier [eight-sentence tunes/base bake-off](../ai-transition/docs/bakeoff-tunes-vs-bases-preregistration-2026-08-25.md) defines S1–W2, with no-extra-human-send completion as its primary measure.
2. The [nine-rung Story Room clerk card](../ai-transition/docs/bench-preregistration-card-2026-09-06.md) names Flash-Next as **Arm B, a later card**. Its current Q/A comparison is unfrozen and concerns the dense 27B. The **September 7 amendment** lets clerk delivery proceed first; the comparison later uses separate branches. Do not reinstate the earlier requirement to hold product merges for both arms.

The general-purpose serving runbook also supports Arm B; its [factory integration and comparison procedure](./QWEN38-software-factory-evaluation.md) is separate. It does not freeze that card or switch the factory. The eventual Q/B card should retain the exact nine sentences, base commits, planted-defect commit, tuned-seat revisions, harness, tools, output budgets, sampling and context policy. First compare with a common **131,072-token harness window** and one active feature. A larger Flash-Next window, additional concurrent builds, thinking on, or different seats would each be another experiment.

Record tasks completed/planned, Player report validity, completion promises, actual file changes, first-turn passes, coach rejections and turns, verifier agreement, extra human sends, generated tokens per completed task and complete wall time. Separate cold load, cold prefill, warm prefix latency, decode, tool/test time and retries. A short tool-call smoke is not the Player's file-writing contract. The [Player assessment](../ai-transition/docs/qwen38-as-player-assessment-2026-08-18.md) explains those contracts, but its August routing description predates the September LiteLLM migration: inspect the executing runner before wiring it.

The local guardkit CLI still exposes `--model` and `--coach-model`; the former can also affect specialist invocations. Therefore verify role attribution in the actual runner and LiteLLM records instead of assuming a model alias edit changes only the Player. The factory's ongoing [sandbox migration](../ai-transition/docs/how-it-works/where-the-factory-runs-2026-09-07.md) also makes “restart the host sidecar” an unsafe universal instruction. The [factory evaluation companion](./QWEN38-software-factory-evaluation.md) covers this application boundary.

## Reproducibility and remaining evidence

The runbook freezes recipe commit `4e1b246aa141e04bd45c20bd1334512988c3770b`, model revision `1f2ba8b30e34097058610938864b1991cfffa24b` and image digest `62a77b7c…15f5bb9`. The registry manifest was fetched and its SHA-256 verified; it contains a Linux ARM64 image. Its OCI revision label is `a35c3cc2935dff63eea8a664509a5931b4b82ea2` (image build), which is intentionally different from the later recipe-document commit. Control-file SHA-256 values were calculated from the pinned HF files. These are artifact checks, not GPU execution results.

Still to measure locally: startup and peak memory, swap traffic, repeated-prefix correctness and latency at factory depths, parser/template behaviour through LiteLLM and the real harness, a full feature's contract compliance, and the Q/B outcome.
