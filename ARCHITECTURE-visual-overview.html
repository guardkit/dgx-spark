dgx-spark / gb10  ·  single-box serving stack

One box · two runbooks · one front door

Every agent talks to :4000. One box does the rest.

A DGX Spark GB10 serving a multi-model fleet from 128 GB of unified memory. The box comes up in two acts: act one stands up the llama-swap :9000 fleet — a complete endpoint on its own — and act two optionally bolts the LiteLLM :4000 control plane on top. Together they are the full community stack (client → LiteLLM → llama-swap → llama.cpp), built on, not stripped down — with one feature deliberately disabled: no cloud fallback, ever.

Why MoE, not dense: the GB10's ~270 GB/s unified-memory bandwidth caps dense models at roughly 8 tok/s — a mixture-of-experts model only moves its active parameters per token (3 B of workhorse's 35 B), which is how the same silicon reaches 31–50 tok/s. That one number shaped the whole fleet.

The same box, in motion

What actually happens when Claude Code asks for claude-sonnet-4-6

No SDK changes, no API key from a cloud console. The agent points base_url at :4000, asks for a Claude model by name, and gets the local workhorse — with the request metered, the swap handled, and no path to a cloud bill.

request gpt-oss-120b → solver picks set big → evict workhorse + embed → cold-load 63 GBhealth window ≤ 600 s → serve ~35 tok/s → idle 600 s → unload → keep-alive revives the fleet

One operator gotcha rides along: the keep-alive timer probes the preloaded fleet every 5 minutes and would happily revive it on top of the 120b — an OOM. Long big-brain runs pause the timer first (systemctl stop llama-swap-keepalive.timer), then resume it after.

fig 4 — the one community feature this box disables

If LiteLLM itself goes down, nothing underneath changes: llama-swap is still serving on :9000, and pointing any agent's base_url there is the documented fallback. The front door is additive — it is never on the critical path.
